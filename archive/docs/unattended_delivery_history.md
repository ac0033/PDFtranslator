# 无人值守交付：现状与能力边界

目标（用户 2026-09-17 确认）：**对常规文本型 PDF 无人值守一次交付可用**。

指导原则：无人值守的本质不是零错误，是零人工兜底；而兜底自动化的前提是失败模式可检测。**出错时系统自己能发现，如实降级或报告，绝不静默交付坏结果。** 扫描件 OCR 明确排除在首版能力边界之外。

推进顺序：① A 稳定性 + D 自动验收单 → ② B 复核规则固化 → ③ C 多样性语料库与边界标定 → ④ 公式识别改进 + LLM 复审层。

**本文件记录第 ①②③④ 步的实际状态。**

## 为什么需要这一步

val.pdf（442 页）的中文版与双语版已交付，但那份"可用"是人工兜底出来的：一次完整生成之后又做了约 6 轮人工复核修补。去掉那 6 轮，一次跑完的成品会带着误译和漏译交付。第 ① 步要解决的是其中两件事——让渲染能自己跑完，让"能不能交付"这个判断不再依赖人。

## A：渲染驱动（`scripts/render_val_full.py`）

BabelDOC 0.6.4 在 Windows 长进程下随机内存分配失败，**根因仍未消除**。现在的做法是把它隔离在有界的子进程里，并让驱动自己处理崩溃。

```bash
# 无人值守跑完整本并合并
uv run python scripts/render_val_full.py --auto \
  --capture output/pdf/<capture-dir> \
  --config configs/<run>.toml \
  --source pdf/<book>.pdf \
  --chunk-size 10 --max-retries 3

# 仍可单块手工渲染 / 单独合并
uv run python scripts/render_val_full.py --from-page 11 --to-page 20 ...
uv run python scripts/render_val_full.py --merge-only ...
```

行为：
- 驱动进程按 `--chunk-size`（默认 10 页）逐块 `subprocess` 调用本脚本自身，每块独立解释器。
- 子进程非零退出或崩溃 → 重跑该块，每块最多 `--max-retries`（默认 3）次。
- **某块重试耗尽不中断整轮**：继续跑完其余块，尽量多抢救页面，最后统一汇报。
- 页级断点语义不变：`page-NNNN/` 下 mono 和 dual **两个**文件都存在才算完成；只写了一个算未完成。
- 全部页就绪后自动合并并写回原书书签；退出码 0；否则打印 `missing_pages` 与失败/重试块清单，退出码非零。

顺带修掉一个既有缺陷：页码范围原先取自最后一个有捕获记录的页，而空白页不产生捕获记录，因此以空白页结尾的 PDF 会少渲染最后一页、随后合并必然因缺页失败。现改为取自源 PDF 页数，空白页走既有的"验证为空则原样插入"路径。val.pdf 因第 442 页早已由手工运行写在磁盘上而未暴露此问题。

val 专属硬编码已参数化（`--runs-root`、`--output-prefix`），默认值保持不变以兼容现有产物路径。

## D：自动验收单（`src/pdf_translation/acceptance.py`）

```bash
uv run pdftrans acceptance-report \
  --source pdf/<book>.pdf \
  --render-dir output/pdf/<capture-dir> \
  --run-id <run_id>            # 可选：与运行库交叉核对复核队列是否过期
```

产出 `acceptance-report.json` + 终端摘要；结论为 `not_deliverable` 时**退出码非零**，供无人值守脚本判断。

判定按 AGENTS.md 第 2 节分级：

**大问题（阻断交付）**：单元处于 `blocked`/`exhausted`/`prepared`/`not_started`；存在 critical 质量问题；单元无译文；源 PDF 某页缺少完整的 mono+dual 渲染产物；合并成品缺失；成品页数与原文不符；复核队列相对运行库过期且隐藏了阻断状态。

**小问题（记录待优化，不阻断）**：needs_review 的 major 项，按 issue category 聚合计数并给代表页码。

**累积升级**：AGENTS.md 第 2 节要求"单处轻微缺陷大量出现应提升为大问题"。实现为**按类别分别设阈值**（占全部单元的比例），而非单一总占比——因为不同类别指示的严重程度差异极大。阈值判定的是**分诊后仍需人工处理的残留量**，不是原始告警量（见下节 B）：

| 类别 | 阈值 | 理由 |
|---|---|---|
| `protected_source_literal_unavailable` | 60% | 公式图形原样保留，这标记的是捕获层的**已知能力边界**，不是译文缺陷；数学教材中天然高频 |
| `number` | 5% | 分词误报消除后，数字清单变化是**真实误译**的最强可用信号 |
| `protected_marker_order` | 5% | 多为中文语序重排（val 44 处中 43 处），但也确实抓到过真实错位 |
| `untranslated_unit` | 5% | AGENTS.md 第 2 节的"整段漏译"大问题 |
| `leaked_markup` | 1% | 字面显示的乱码 |
| `retained_english` | 30% | 咨询性信号，检测器有实测噪声，因此不用于阻断 |
| `url` / `terminology` | 2% | 直接改变含义 |
| 未列出的新类别 | 5%（默认） | 未知即从严 |
| 残留总占比 | 80% | 兜底 |

阈值可通过 `build_acceptance_report(thresholds=...)` 覆盖，且原样写进报告。

**报告明确声明未检查什么**（AGENTS.md 第 5 节）：译文是否忠实于原文、保留的公式图形是否贴在正确的文字旁、页面呈现与页数之外的版面质量，均**不在自动检查范围**。报告给出仍需人工对照原书的公式占位符数量及涉及页数。

## B：复核规则固化与复核台账（第 ② 步）

第 ① 步的验收单能判断"能不能交付"，但**不判断译文对错**——val 那 6 轮人工复核查出的问题它一个也抓不出来。第 ② 步处理的就是这件事。

原则：**不凭直觉消除任何告警**。只有两种情况可以消除：

1. **规则证明告警是检查自身的产物**。质量门的数字检查用 `(?<![A-Za-z0-9_])` 前后视取数字清单，所以粘着字母的数字在英文侧看不见、在中文侧看得见：`Figure2.1` 取不到，`图2.1` 取到 `2.1`。用容忍粘连的模式重读两侧，这一类就消失了。
2. **人已经判定无害**，记在复核台账里，且**仅在文本未变期间有效**（按 result_hash 键控，重译即失效）。

### 量化验证（`tests/test_triage.py` 对真实标注断言）

标注语料是 2026-09-16/17 人工复核的全部产出，已从被 gitignore 的 `tmp/` 固化进 `tests/data/`——**那是本项目仅有的人工标注，此前一次断电就会丢失**。

| 指标 | 结果 |
|---|---|
| 被规则消除的真实错误 | **0 / 5**（安全属性，测试中不可放宽） |
| 被规则消除的分词误报 | 67 / 77（87%） |
| 等值换算（`$370 million`→`3.7亿`）保守保留 | 6 / 6 |
| 全书数字告警 | 136 → 20 待人工（叠加台账后 → **1**） |
| 标记顺序告警 | 44 → **0**（43 条台账消除，1 条已修复不再触发） |

### 新增的三类信号（质量门此前完全没有）

| 信号 | 说明 | val 结果 |
|---|---|---|
| `untranslated_unit` | 译文仍以拉丁字符为主的单元，排除文献条目（按**原文形态**判定，与语言无关） | 21 个（0.4%） |
| `leaked_markup` | 译文里出现而原文没有的标记标签 | 1 个（第 93 页 `<term>定义</term>`，真实缺陷） |
| `retained_english` | 中文行文里残留的英文，**按术语分组**（决策本来就是按术语做的：rollout 要么处处错要么处处不错） | 300 单元 / 231 术语（咨询性，有已知噪声） |

`untranslated_unit` 对应 AGENTS.md 第 2 节的"整段漏译"大问题，此前**没有任何自动检测**。

### 试过并否决的两条规则（记录下来避免重复踩坑）

- **按全书一致性分诊英文残留——不成立**。系统性漏译本身也是一致的：val 中 `rollout`（真实漏译）保留率 0.91，而 `for`（Julia 关键字，正确保留）保留率 0.04，完全分不开。只有逐文档术语表能区分。
- **标记顺序自动裁决——数据不足**。44 例中只有 1 例真实，单个正例无法验证任何规则，因此不提供，全部保留为待人工。

### 验收单读错了证据：改为以运行库为准

第 ① 步的验收单读 `content-review.jsonl`。该文件是渲染时的快照，**此后的 curated-TM 修复只进运行库和成品页，不回写快照**：val 有 **25 个单元**（含全部 5 处已确认的数字错误）在快照里仍是坏的，而磁盘上的成品早已修好。按那份文件打分，描述的是一本谁也没交付过的书。

现在传 `--run-id` 时以运行库为准，快照只用于不会变的信息（单元覆盖哪些页），并如实报告快照陈旧了多少单元。不传 `--run-id` 时，报告会写明"本结论仅基于快照文件，陈旧性未经检查"。

### 用法

```bash
# 一次性：把 2026-09 的人工复核转成台账（provenance 见脚本 docstring）
# 按书目准备复核台账（JSON，见下文格式）

# 验收时带上运行库与台账
uv run pdftrans acceptance-report \
  --source pdf/val.pdf \
  --render-dir output/pdf/val-usable-babeldoc-full-r1 \
  --run-id val-usable-full-r1 \
  --review-ledger <review-ledger>.json
```

## C：捕获层覆盖度对账（第 ③ 步）

这是此前最大的盲区。项目里其他所有检查都以**翻译单元**为对象，而捕获层没交出来的文本**根本没有单元**——它不会被阻断、不会被告警、不会进复核队列，只会以原文形态印在成品上，而报告说一切正常。val.pdf 第 105 页那 4 个真值表单元格就是这么丢的，最后靠人读出来。

### 做法：第二意见

pymupdf 独立于 BabelDOC 解析同一页；**第一个提取器看得见、第二个从未交付**的文本就是捕获缺口。

三类文本被排除，因为管线是刻意保留它们的，报上来只会把真缺口淹掉（val 原始差异 2816 处，排除后剩 130 处）：

| 排除项 | 判别方式 |
|---|---|
| 代码 | 等宽字体（val 的 Julia 代码块占原始差异的绝大部分） |
| 公式字形 | 数学字体（CM*/MSAM/EUR/*Math*/Pazo 等） |
| 算子名 | LaTeX 标准算子集（`\log`、`\arg`、`\max` …）+ cases 环境里 `\text{}` 的少数词。它们用正文字体排版，但属于公式 |

**无法识别的字体按正文处理**——排除认不出来的东西，恰好会藏住这个检查存在的意义。

### val.pdf 实测

**92,040 个正文词中 130 个未被捕获（0.141%）**，分布在 48 页，其中 11 页有 ≥3 处。除了已知的第 105 页，还查出**两个此前无人知道、更严重的缺口**：

| 页 | 未捕获 | 占该页正文 | 内容 |
|---|---|---|---|
| 88 | 27 | 23.3% | `true` ×27（真值表整列未捕获） |
| 396 | 14 | 15.2% | `pred` ×10、`true` ×4 |
| 61 | 10 | 15.9% | `true` ×8 |
| 177 | 7 | 4.1% | `fail` ×6 |
| 105 | 4 | 1.9% | `true` ×4（此前已知的那个） |

阈值设为**全书正文的 1%**：超过即判为大问题（书里有未翻译内容，且没有别的检查能看见）。val 的 0.141% 有约一个数量级的余量。

用法：

```bash
uv run pdftrans capture-coverage --source pdf/<book>.pdf --capture-map output/pdf/<dir>/capture-map.jsonl
```

验收单在 `capture-map.jsonl` 存在时**默认运行**该对账（全书 2.5 秒），结果进 `acceptance-report.json` 的 `capture_coverage` 段。

### 多样性语料标定

捕获是**本地操作、零 API 成本**，所以跨文档量化捕获层的通用性不需要花钱。每本书按确定性规则抽取中段 12 页（抽样脚本）：

| 文档 | 页数 | 抽样 | 未捕获正文 | 占比 |
|---|---|---|---|---|
| val.pdf | 442 | 12 | 2 / 2719 | 0.074% |
| dm.pdf | 700 | 11 | 2 / 1830 | 0.109% |
| cs224n 讲义 | 18 | 12 | 2 / 2719 | 0.074% |
| **optimization.pdf** | 634 | 12 | **10 / 1729** | **0.578%** |

四本书**全部低于 1% 阈值**，但 optimization.pdf 差 5–8 倍。查下来是**体裁效应**：优化问题陈述里大量 `\text{minimize}`、`\text{subject to}`，用正文字体排版却属于公式。据此把 `minimize`/`maximize` 补进算子集——依据与已有的 `otherwise` 完全一致，不是针对单本调参。这正是多样性语料该起的作用：**第二本书暴露了第一本书看不见的模式**。补入后 optimization 从 0.864% 降到 0.578%，val 从 0.151% 降到 0.141%，关键缺口（88/396/61/177/105 页）全部保留。

**一次真实的环境失败值得记录**：optimization.pdf 第一次跑**彻底失败**（`RuntimeError: no such file: ...\input.pdf`，耗时 603 秒后报错）。根因是 BabelDOC 的临时文件走**系统 TEMP（C 盘）**，而当时 C 盘已满。把 TEMP 指到有空间的盘后一次通过。记录它不是因为文档不受支持，而是因为**无人值守的管线必须扛住这种事**。泄漏的根因已在提交 `2fe911a` 中修复（见下文遗留问题第 5 条），但空间预检与临时目录配置仍缺。

这份标定**只覆盖捕获层**。它不证明这些文档能端到端翻译：那需要付费运行，本脚本刻意不发起。

## ④-1：公式上下文恢复（零 API 成本）

先澄清一件之前没查清的事：`protected_source_literal_unavailable` 里那 1466 个"公式"，**保护标记存的"原文"就是占位符本身**——全书 5133 个标记都是 `<bN>` 形态，只对应 49 个不同的 sha256，正是 `<b1>`、`<b2>`…… 的哈希。真正的公式字形从不进入文本流，BabelDOC 把它们作为图形保留。所以模型在翻译时看到的是一个**完全不透明的标记夹在句子中间**，只能靠上下文猜这句在说什么。

唯一的恢复途径就是从页面字形里读，也就是 `protected_literals.py` 在做的锚定匹配。先量化 3998 个未恢复标记卡在哪：

| 卡点 | 数量 | 占比 |
|---|---|---|
| bbox 置信度不足（< 0.85，直接不尝试） | 1877 | 46.9% |
| 锚点文本过短（< 8 字符） | 1809 | 45.2% |
| 恢复到了但"不可信"（`sys`、`step`、`Turing.jl`） | 288 | 7.2% |
| 其余（锚点找不到、歧义、过长） | 24 | 0.6% |

两处放宽，**都不削弱"唯一锚定"这个保证**：

1. **bbox 不可信时改为整页匹配**。要求锚点在**整页**只匹配一次，比信任一个低置信度的框**更强**，不是更弱。
2. **代码标识符算可信上下文**。`sys`、`step`、`Turing.jl` 没有数字也没有数学符号，但"the `sys` function"这句话不知道 `sys` 就没法翻。

刻意**没有**放宽锚点长度（8 字符）——那正是唯一性保证的来源。测过放宽到 3 字符能到 31.2%，收益不值这个风险。

测试抓到一个真实弱点：匹配在**去空格**的文本上进行，于是 `very slow and careful routine` 压成一串后长得像标识符。因此标识符要过第二关——**必须在页面原始文本里原样出现**（含空格）。数学字面量豁免，因为 `= 1` 本来就是分开排、连起来读的。

还修了一个加宽 gap 引入的退化：gap 变宽会多出对齐方式，而多标记整体路径要求**所有**分组都可信，一处不可信就整体作废。改为**优先用能解释所有标记的最紧边界**，紧的不行再放宽。

### 实测（对已交付的 val 捕获重跑）

| 指标 | 结果 |
|---|---|
| 标记恢复 | **1135 → 1594 / 5133（22.1% → 31.1%）** |
| 新恢复 | **+459**（标识符 320、数学/脚注 136） |
| 丢失 | **0** |
| 改变了现有结论 | **0** |

新恢复的典型值：`Turing.jl`、`sys`、`step`、以及大量脚注编号。这些会通过 `<protected-source-literals>` 进入翻译提示词，**直接提升后续运行的译文质量**；已交付的 val 不受影响（不重译）。

## ④-2：LLM 复审层（已实现，未花钱）

`src/pdf_translation/warning_review.py`。思路是 Kimi 建议的：**只问"这条告警是不是真问题"**，一条告警一次短调用，比全量翻译便宜几个数量级。

三条硬约束：

1. **证据必须逐字引用**。判定要给出 source 和 target 里的精确子串，在本地校验。指不出文本的模型没有裁定权——与既有 `semantic_review.py` 同一套契约。
2. **模型永远不能自己消除告警**。裁定以 `reviewed_by: model:<id>` 记入台账，验收单**单独计数**，默认**仍留在人工清单上**，只是把模型的理由和引用挂上去。AGENTS.md 第 5 节禁止靠忽略检查取得"通过"，而模型说"没问题"不构成"确实没问题"的证据。要信任它必须显式 `trust_model_verdicts=True`。
3. **不问模型答不了的问题**。`protected_source_literal_unavailable`（1466 条）**被明确排除**：那个公式模型和管线一样读不到，答案只能是猜，而**披着裁定外衣的猜测比一个公开的未知更糟**。`retained_english`（300 条）也排除：某个术语该不该保留英文是**全书一个决定**，不是 300 个独立问题，它属于术语表。

预算门复用既有 `budget.py`：估算超预算直接拒绝启动。校验失败的裁定记为 failure 而非静默丢弃。

## 换一本书：optimization.pdf 暴露的三个缺口

目标是"对**常规文本型 PDF** 无人值守一次交付可用"，而此前端到端只跑过 val.pdf 一本。拿 optimization.pdf（634 页，抽第 150–269 页共 120 页）来验证，**第一次跑就失败了**——这正是换一本书的意义。

### 1. 捕获阶段没有崩溃防护

```
RuntimeError: code=2: realloc (3405097 bytes) failed
```

第 ① 步给**渲染**做了子进程隔离 + 有界重试，**捕获没有**：`capture_val_full.py` 虽然分块、可续跑，但那个循环跑在**同一个进程里**，内存压力照样累积。val.pdf 当年是靠人手工分批跑绕过去的，所以这个洞一直没暴露；换一本书，第一块 20 页就倒了。

修法不是在捕获脚本里再抄一遍渲染的驱动，而是把它提到包里：`src/pdf_translation/chunk_driver.py`，**渲染和捕获共用同一份**。复制一遍的代价是只修一边——这次就是这么漏的。

### 2. 捕获脚本只支持整本

`expected_chunks` 按全书页数算、`physical_pages` 硬写 1..N，所以捕获一个**页范围**会在合并阶段永远等不齐。现在页范围是一等输入，`--total-pages` 默认从 PDF 自己读，`--capture-root` 可配置。

### 3. 资源不足时死得不知所云

```
OpenBLAS error: Memory allocation still failed after 10 retries, giving up.
```

真实原因是 Windows 的**提交内存（commit charge）耗尽**——上限 36.9 GB 已用 36.8 GB，物理内存却还有 2.3 GB 空闲。**看空闲内存是看不出来的**，Windows 按 commit 限额拒绝分配。而这条报错既不指向原因也不指向解法，无人值守下等于跑十分钟后拿到一句天书。

现在 `--auto` 启动前预检提交内存，不够就**一秒内**报清楚数字：

```
MemoryError: only 839 MB of commit headroom, need 2048 MB. Free memory before
starting: a long BabelDOC run dies inside OpenBLAS with an error that names
neither the cause nor the cure.
```

阈值是**实测**来的，不是拍的：366 MB 余量时连一页都读不到就死在 OpenBLAS；1563 MB 时两页捕获正常完成（264 秒 / 31 单元）。2 GB 是这个下界加余量，并且只是默认值——`--min-free-mb` 可以调低，因为**拦住一个本来能跑完的任务同样是一种失败**。

### 4. 一个分块进程把自己当成了整本书（2026-09-18）

捕获跑起来之后，日志里 **42 次 `FileExistsError`**，每一块都"失败"了三次——而底下的捕获数据其实一直在正常落盘。

根因在 `capture_val_full.py`：子进程能看见磁盘上别的分块的产物，却不知道这一轮**总共该有几块**。它拿"现有块数"去比自己那 10 页范围算出来的期望块数（永远是 1），于是 **第一块 150–159 一捕获完就认定全书齐了**，把自己的 129 个单元合并成了 `output/pdf/opt-slice-r1`。之后每一块撞上"输出目录已存在"退出码非零，驱动把它当崩溃，各重试 3 次。

这是第 ② 类问题的翻版：**分块是新加的，但"谁负责合并"没跟着定义**。现在合并归持有完整页范围的那个进程，子进程带 `--capture-only` 启动、写完自己的产物就停；完整性改为按页范围**点名**检查每个分块目录，缺块报名字而不是被一个刚好凑齐的计数掩盖。

`tests/test_capture_driver.py` 钉住这个行为——去掉修复后 6 个测试挂 5 个。

### 5. 切片在捕获之后的每一步都不是一等公民（2026-09-18）

捕获支持页范围了，**下游四处仍然假设"整本书"**，都是同一个写法：从源 PDF 读总页数。对 634 页书的 120 页切片，这四处会分别：

| 位置 | 后果 |
|---|---|
| `render_val_full.py` 合并 | 要求 634 页齐全，切片永远合并不了 |
| `acceptance.py` 渲染判定 | 报 514 页缺失 + 两本书页数不符 → 假的 `not_deliverable` |
| `acceptance.py` / `capture-coverage` 覆盖度对账 | 把其余 514 页报成"捕获丢失的正文"——属实，且毫无用处 |
| 合并时写回书签 | 切片页码从 1 重排，整本书的目录指向不存在的页 |

现在这四处统一读**捕获自己的报告**（`capture.report.json` 的 `physical_pages`）：它记的是"当初要的范围"而不是"产生了记录的页"，所以末尾空白页仍然进书。这个 helper 放在 `acceptance.py`，和页级断点契约挨着，渲染脚本 import 它——**判定和合并必须对"这一轮负责哪些页"意见一致**，否则一个完整的切片看起来就像一本有洞的书。

切片的合并现在会如实报告自己的页范围，并明说书签被丢掉了，而不是留一份静默错误的目录。

### 6. 质量门要求译文做到源文自己做不到的事（2026-09-18）

第一次完整跑通 optimization.pdf 切片后，1473 个单元里 **8 个始终没拿到译文**，连带 120 页里 **50 页没渲染、整本书出不来**。

**不是网络、不是预算、不是输出截断**——每次调用都正常返回、token 也没打满，是被质量门判无效，各重试 3 次后钉成 `exhausted`。

其中 7 个死在 `layout_boundary`。这条检查要求每个版面标记前的文字在**句末**结束。但这本书里展示公式会把一个英文句子劈开：

```
⟦版面A⟧...Proximal minimization applied to this yields ⟦版面B⟧where
```

源文自己的边界就落在半句上，`rebalance_layout_markers` 没有句末可挪。**任何译文都不可能通过**——模型被要求做了三次不可能的事。全书 1473 个单元里有 37 个是这种版面。

修法：这条检查**只在源文自己满足时才执行**；源文不满足时记为 `layout_boundary_unverifiable`，进验收报告的"未能检查"一栏，而不是"发现的缺陷"。

修的过程中发现这条检查还在**兼职**干另一件事：抓"公式槽被改动"。公式型单元是原样透传的，译文与源文不同就说明那段文字不是翻译出来的。这条规则现在显式写成独立的 critical 检查（`formula_slot_changed`），不再寄生在一条关于句号的规则上。

### 7. 一个规则修好了，却救不回被它判死的单元（2026-09-18）

`exhausted` 是钉死的——重跑会跳过。规则不变时这是对的（不该为同一次拒绝付两次钱），**规则一改就错了**：那个判决针对的规则已经不存在，单元却永远翻译不出来，页也永远渲染不出来。

新增 `pdftrans retry-exhausted --run-id <id>`：解钉，并清掉已记录的尝试次数（运行器也会查这个额度）。实测 **8 → 2**，重试成本 $0.006。

### 8. 一个段落带走十页（2026-09-18）

渲染分块只要有一个单元没有译文就整块拒绝。**2 个单元（0.14%）因此让 20 页渲染不出来**，第一次更是 8 个单元带走 50 页、整本书出不来。

这不符合"如实降级"：无法翻译的单元现在**回退成它自己的源文**（源文带着同样的标记，注入是干净的）。那一页照常渲染，只是那个段落还是英文；验收报告仍然从运行库读出它是未翻译单元。**降级是公开的，绝不冒充完成。**

|---|---|---|

| 234 | 数字漏译 | `中间的容差ϵ = 0在两种极端之间取得了平衡`（应为 `ϵ = 0.001`） |

### 9. 质量门没有"译文自己造出来的标记"这项检查

第 93 页那个单元在质量门里是 **`accepted`、零 issues**——`leaked_markup` 检测器只存在于 triage 层，而 triage 在书印出来之后才跑。**模型从来没有机会重试它。**

检测器提到质量门里，判 critical：这是模型第二次尝试就能修好的结构性缺陷，和丢标记同类。模式 `MARKUP_TAG` 挪到 `quality.py` 与其他清单模式作伴，triage 反过来引用它。

### 10. 中文语序把标记挤出了它该在的文本框

optimization.pdf 第 207 页三次尝试**每次都返回了全部 7 个标记、版面顺序也全对**，却每次都被 `protected_marker_order` 判 critical 丢弃：

```
源文：...our constraint is satisfied⟦o000⟧when y⟦o001⟧:m...
译文：...当 y⟦o001⟧:m ⟦o002⟧L⟦o003⟧b 时，我们的约束得到满足⟦o000⟧。
```

脚注标号 `⟦o000⟧` 跟着"得到满足"移到了后面——**这是正确的中文**，条件从句本来就该前置。

两处修改：

1. **判定按理由来**。判 critical 的理由本是"跨版面边界会把标记塞进错误的 PDF 文本框"。现在就按这个判：标记**换了片段**才是 critical，片段内部换位置是 major。新增 `marker_fragments()`。
2. **新增按片段安放的确定性修复**（`place_layout_markers_by_fragment`）。已有的 `restore_and_rebalance_layout_markers` 一看到非版面标记顺序变了就放弃——而中文重排是常态。新函数只要求**每个标记回到它原来的框**，框内顺序归译文管；窗口里没有句末可切时仍然放弃（硬切会把大半段塞进只容一行的框，第 172 页就是这种）。

### 附：val.pdf 当初的风格提示

`translate_val_usable_sample.py` 原先把 val 专属的风格提示写死在代码里。通用化之后它变成 `--style-note`，默认为空。val 当初用的原文记录在此，以备复现：


（rule_id 也从 `val-usable-style-<doc>` 变成 `{sample_name}-style-<doc>`。val 的成品已交付、风格规则已存进上下文库，不计划重跑。）

## 本步骤明确未解决的问题

1. **BabelDOC 内存崩溃根因未消除**，仅做了进程隔离 + 自动重试。换机器、换文档仍可能复发，只是不再需要人盯着。
2. **语义判定仍未真正到位**。④-2 把"这条告警是不是真问题"变成可问、可验证、可记账的一次调用，但**尚未真实跑过**（见上文，需你授权 0.0094 美元）。而且它只覆盖 23 条告警；1466 条公式占位符**按设计不问**——模型读不到那个公式，这是能力边界，不是待办。
   此外 B 的规则全部从 **val.pdf 一本书**的 165 条人工裁定中蒸馏而来。`glued_digit_tokenisation` 是对质量门正则的结构性修正、可放心推广；其余参数（术语文档频率 2%、拉丁占比 40%/50%、文献条目判定）只在这一本上量化过。
3. ~~**捕获层覆盖度无度量**~~（第 ③ 步已解决，见上文 C 节）。遗留限制：对账只覆盖**字母词**，数字被排除（技术书里绝大多数数字属于公式）；图注、示意图内的文字与真值表单元格无法区分，二者都会被报出来等人判断。
4. **通用性只验证到捕获层**。4 本书的捕获覆盖度已标定（见上表），但**端到端**（翻译→质量门→渲染→验收）仍只有 val.pdf 一本。B 的分诊参数、D 的各类阈值都只在 val 上量化过。端到端验证需要付费运行，未经授权不启动。
5. **临时目录仍不可配置、空间不预检**。optimization.pdf 那次失败暴露了这条链路：BabelDOC 走系统 TEMP，磁盘满时抛一个看不出根因的 `no such file` 错误。
   其**根因（Windows 文件句柄导致 BabelDOC 的工作目录清不掉、一周累积 1115 个目录 / 28.4 GB）已由提交 `2fe911a` 修复**——该提交来自同日另一个会话，改为 gc + 退避重试并在残留时告警，实测残留稳定在一个 ~620 KB 目录。
   仍未解决的是：管线**不预检可用空间**，也**不允许配置临时目录位置**（只能靠外部设 `TMP`/`TEMP` 环境变量绕开）。无人值守下磁盘一满，仍会变成一次跑了十分钟、什么都没产出、错误信息还指不到根因的失败。
6. `--auto` 的完整链路**未在真实 442 页上端到端跑过**：val 的页级产物早已齐备，重跑会覆盖唯一可回退成品，因此只做了非破坏性核对（442/442 页断点齐全、分块计划覆盖全书）。驱动逻辑本身由 `tests/test_render_driver.py` 用假子进程覆盖成功/崩溃重试/重试耗尽三条路径。

## 据实区分

- **文件已生成**：`acceptance-report.json` 可对任意已渲染产物生成。
- **可用版本已通过**：val.pdf 的两个成品经自动验收判定为 `deliverable_with_known_issues`。
- **无人值守能力已具备**：**部分**。渲染能自己跑完、交付判断能自动做出、人工复核清单已从 213 条降到约 23 条，且台账让重跑同一本书收敛到接近零。但**首次跑一本新书仍需人看那 23 条**，且捕获层漏捕获仍不可见（第 3 点）。"一次跑完即可交付、无人介入"尚未成立。
- **版本已发布**：否。

## 一条命令跑完一份 PDF，并记录各阶段耗时

入口：`scripts/deliver_pdf.py`，依次执行抽取 → 覆盖度核对 → 翻译 → 渲染 → 验收，各阶段耗时写入输出目录旁的 `<输出目录>.timings.json`。每个阶段都可断点续跑：同一条命令重跑时从磁盘上已有的结果继续。

```bash
uv run python -m scripts.deliver_pdf --source pdf/<文件>.pdf --config configs/<配置>.toml   --style-note-file configs/<风格说明>.txt --workers 3
```

| 参数 | 作用 |
|---|---|
| `--workers N` | 抽取与渲染同时运行的进程数；每个进程按 2 GB 可提交内存计，超出时自动下调 |
| 配置里的 `translation_concurrency` | 同时发出的翻译请求数（默认 1）；只影响速度，不进 `config_hash`，已有运行可直接调高后续跑 |

### 实测：14 页讲义（`cs224n-2019-notes05-LM_RNN.pdf`，285 个翻译单元），4 核笔记本，插电

| 阶段 | 串行、每 10 页一个进程 | `--workers 3`，`translation_concurrency = 8` |
|---|---|---|
| 抽取 | 约 8.5 分钟（35.9 s/页） | 91 s |
| 翻译 | 373 s | 85 s |
| 渲染 | 约 9 分钟（37.8 s/页） | 113 s |
| 合计 | 约 23 分钟 | **约 4.9 分钟** |

串行一列的抽取与渲染按同机插电时单进程逐页测得的速度折算。电池供电时抽取慢 4 倍以上，长任务应插电运行。翻译费用约 USD 0.10。

### 实现要点（均不改变产出：抽取记录逐条一致，渲染 PDF 逐像素一致）

1. **翻译并发**：只有调用 API 的部分进线程池；数据库写入串行；预算检查计入在途请求的费用上限，并发不会超支（`tests/test_pipeline_concurrency.py`）；账号或预算类故障停止尚未发出的请求，单段重试用尽不影响其他段。
2. **抽取不生成 PDF**：抽取只需要 BabelDOC 交给翻译回调的段落，排版、字体子集化和保存（Windows 上每次保存新开一个 Python 进程）都跳过。
3. **每个进程只校验一次字体**：BabelDOC 每页约 200 次对字体文件重算 SHA3-256，并各开一个线程与事件循环；成功结果按进程缓存，失败不缓存。
4. **本地翻译回调不限速**：BabelDOC 全局限速默认每秒 5 段；本项目在抽取与渲染阶段交给 BabelDOC 的都是本地回调，不经过任何 API。
5. **分块多进程并行**：抽取与渲染的分块写入互不重叠的页，可以同时运行。

### 已知的剩余开销

- BabelDOC 每次保存 PDF 都新开 Python 子进程（Windows 上每次约 2–3 s，每页 3–4 次），用于给 `clean=True` 保存设超时；改为进程内保存需要另设防卡死保护。
- 每页约 10 s 用于反复创建 `pymupdf.Font` 对象；缓存它需要共享 BabelDOC 会修改的字体对象或整个 FontMapper，有状态污染风险。
- 翻译阶段受单段最慢请求与重试长尾限制，并发 8 相比串行约 4.4 倍。
