# 无人值守交付：现状与能力边界

目标（用户 2026-09-17 确认）：**对常规文本型 PDF 无人值守一次交付可用**。

指导原则：无人值守的本质不是零错误，是零人工兜底；而兜底自动化的前提是失败模式可检测。**出错时系统自己能发现，如实降级或报告，绝不静默交付坏结果。** 扫描件 OCR 明确排除在首版能力边界之外。

推进顺序：① A 稳定性 + D 自动验收单 → ② B 复核规则固化 → ③ C 多样性语料库与边界标定 → ④ 公式识别改进 + LLM 复审层。

**本文件记录第 ①② 步的实际状态。第 ③④ 步尚未开始。**

## 为什么需要这一步

val.pdf（442 页）的中文版与双语版已交付，但那份"可用"是人工兜底出来的：一次完整生成之后又做了约 6 轮人工复核修补（详见 `v0.7_rc14_current_status.md`）。去掉那 6 轮，一次跑完的成品会带着误译和漏译交付。第 ① 步要解决的是其中两件事——让渲染能自己跑完，让"能不能交付"这个判断不再依赖人。

## A：渲染驱动（`scripts/render_val_full.py`）

BabelDOC 0.6.4 在 Windows 长进程下随机内存分配失败，**根因仍未消除**。现在的做法是把它隔离在有界的子进程里，并让驱动自己处理崩溃。

```bash
# 无人值守跑完整本并合并
uv run python scripts/render_val_full.py --auto \
  --capture output/pdf/<capture-dir> \
  --config configs/<run>.toml \
  --source pdf/<book>.pdf \
  --chunk-size 10 --max-retries 3

# 仍可单块手工渲染 / 单独合并
uv run python scripts/render_val_full.py --from-page 11 --to-page 20 ...
uv run python scripts/render_val_full.py --merge-only ...
```

行为：
- 驱动进程按 `--chunk-size`（默认 10 页）逐块 `subprocess` 调用本脚本自身，每块独立解释器。
- 子进程非零退出或崩溃 → 重跑该块，每块最多 `--max-retries`（默认 3）次。
- **某块重试耗尽不中断整轮**：继续跑完其余块，尽量多抢救页面，最后统一汇报。
- 页级断点语义不变：`page-NNNN/` 下 mono 和 dual **两个**文件都存在才算完成；只写了一个算未完成。
- 全部页就绪后自动合并并写回原书书签；退出码 0；否则打印 `missing_pages` 与失败/重试块清单，退出码非零。

顺带修掉一个既有缺陷：页码范围原先取自最后一个有捕获记录的页，而空白页不产生捕获记录，因此以空白页结尾的 PDF 会少渲染最后一页、随后合并必然因缺页失败。现改为取自源 PDF 页数，空白页走既有的"验证为空则原样插入"路径。val.pdf 因第 442 页早已由手工运行写在磁盘上而未暴露此问题。

val 专属硬编码已参数化（`--runs-root`、`--output-prefix`），默认值保持不变以兼容现有产物路径。

## D：自动验收单（`src/pdf_translation/acceptance.py`）

```bash
uv run pdftrans acceptance-report \
  --source pdf/<book>.pdf \
  --render-dir output/pdf/<capture-dir> \
  --run-id <run_id>            # 可选：与运行库交叉核对复核队列是否过期
```

产出 `acceptance-report.json` + 终端摘要；结论为 `not_deliverable` 时**退出码非零**，供无人值守脚本判断。

判定按 AGENTS.md 第 2 节分级：

**大问题（阻断交付）**：单元处于 `blocked`/`exhausted`/`prepared`/`not_started`；存在 critical 质量问题；单元无译文；源 PDF 某页缺少完整的 mono+dual 渲染产物；合并成品缺失；成品页数与原文不符；复核队列相对运行库过期且隐藏了阻断状态。

**小问题（记录待优化，不阻断）**：needs_review 的 major 项，按 issue category 聚合计数并给代表页码。

**累积升级**：AGENTS.md 第 2 节要求"单处轻微缺陷大量出现应提升为大问题"。实现为**按类别分别设阈值**（占全部单元的比例），而非单一总占比——因为不同类别指示的严重程度差异极大。阈值判定的是**分诊后仍需人工处理的残留量**，不是原始告警量（见下节 B）：

| 类别 | 阈值 | 理由 |
|---|---|---|
| `protected_source_literal_unavailable` | 60% | 公式图形原样保留，这标记的是捕获层的**已知能力边界**，不是译文缺陷；数学教材中天然高频 |
| `number` | 5% | 分词误报消除后，数字清单变化是**真实误译**的最强可用信号 |
| `protected_marker_order` | 5% | 多为中文语序重排（val 44 处中 43 处），但也确实抓到过真实错位 |
| `untranslated_unit` | 5% | AGENTS.md 第 2 节的"整段漏译"大问题 |
| `leaked_markup` | 1% | 字面显示的乱码 |
| `retained_english` | 30% | 咨询性信号，检测器有实测噪声，因此不用于阻断 |
| `url` / `terminology` | 2% | 直接改变含义 |
| 未列出的新类别 | 5%（默认） | 未知即从严 |
| 残留总占比 | 80% | 兜底 |

阈值可通过 `build_acceptance_report(thresholds=...)` 覆盖，且原样写进报告。

**报告明确声明未检查什么**（AGENTS.md 第 5 节）：译文是否忠实于原文、保留的公式图形是否贴在正确的文字旁、页面呈现与页数之外的版面质量，均**不在自动检查范围**。报告给出仍需人工对照原书的公式占位符数量及涉及页数。

## B：复核规则固化与复核台账（第 ② 步）

第 ① 步的验收单能判断"能不能交付"，但**不判断译文对错**——val 那 6 轮人工复核查出的问题它一个也抓不出来。第 ② 步处理的就是这件事。

原则：**不凭直觉消除任何告警**。只有两种情况可以消除：

1. **规则证明告警是检查自身的产物**。质量门的数字检查用 `(?<![A-Za-z0-9_])` 前后视取数字清单，所以粘着字母的数字在英文侧看不见、在中文侧看得见：`Figure2.1` 取不到，`图2.1` 取到 `2.1`。用容忍粘连的模式重读两侧，这一类就消失了。
2. **人已经判定无害**，记在复核台账里，且**仅在文本未变期间有效**（按 result_hash 键控，重译即失效）。

### 量化验证（`tests/test_triage.py` 对真实标注断言）

标注语料是 2026-09-16/17 人工复核的全部产出，已从被 gitignore 的 `tmp/` 固化进 `tests/data/`——**那是本项目仅有的人工标注，此前一次断电就会丢失**。

| 指标 | 结果 |
|---|---|
| 被规则消除的真实错误 | **0 / 5**（安全属性，测试中不可放宽） |
| 被规则消除的分词误报 | 67 / 77（87%） |
| 等值换算（`$370 million`→`3.7亿`）保守保留 | 6 / 6 |
| 全书数字告警 | 136 → 20 待人工（叠加台账后 → **1**） |
| 标记顺序告警 | 44 → **0**（43 条台账消除，1 条已修复不再触发） |

### 新增的三类信号（质量门此前完全没有）

| 信号 | 说明 | val 结果 |
|---|---|---|
| `untranslated_unit` | 译文仍以拉丁字符为主的单元，排除文献条目（按**原文形态**判定，与语言无关） | 21 个（0.4%） |
| `leaked_markup` | 译文里出现而原文没有的标记标签 | 1 个（第 93 页 `<term>定义</term>`，真实缺陷） |
| `retained_english` | 中文行文里残留的英文，**按术语分组**（决策本来就是按术语做的：rollout 要么处处错要么处处不错） | 300 单元 / 231 术语（咨询性，有已知噪声） |

`untranslated_unit` 对应 AGENTS.md 第 2 节的"整段漏译"大问题，此前**没有任何自动检测**。

### 试过并否决的两条规则（记录下来避免重复踩坑）

- **按全书一致性分诊英文残留——不成立**。系统性漏译本身也是一致的：val 中 `rollout`（真实漏译）保留率 0.91，而 `for`（Julia 关键字，正确保留）保留率 0.04，完全分不开。只有逐文档术语表能区分。
- **标记顺序自动裁决——数据不足**。44 例中只有 1 例真实，单个正例无法验证任何规则，因此不提供，全部保留为待人工。

### 验收单读错了证据：改为以运行库为准

第 ① 步的验收单读 `content-review.jsonl`。该文件是渲染时的快照，**此后的 curated-TM 修复只进运行库和成品页，不回写快照**：val 有 **25 个单元**（含全部 5 处已确认的数字错误）在快照里仍是坏的，而磁盘上的成品早已修好。按那份文件打分，描述的是一本谁也没交付过的书。

现在传 `--run-id` 时以运行库为准，快照只用于不会变的信息（单元覆盖哪些页），并如实报告快照陈旧了多少单元。不传 `--run-id` 时，报告会写明"本结论仅基于快照文件，陈旧性未经检查"。

### 用法

```bash
# 一次性：把 2026-09 的人工复核转成台账（provenance 见脚本 docstring）
uv run python scripts/seed_val_review_ledger.py

# 验收时带上运行库与台账
uv run pdftrans acceptance-report \
  --source pdf/val.pdf \
  --render-dir output/pdf/val-usable-babeldoc-full-r1 \
  --run-id val-usable-full-r1 \
  --review-ledger reports/val_review_ledger.json
```

## 本步骤明确未解决的问题

1. **BabelDOC 内存崩溃根因未消除**，仅做了进程隔离 + 自动重试。换机器、换文档仍可能复发，只是不再需要人盯着。
2. **验收单仍不判断译文对错**。B 让它能指出"这一处需要人看"，但不能判定"这处译得对不对"。数字清单一致不等于译文正确；`retained_english` 只列出术语，不判定该不该译；等值换算（`$370 million`→`3.7亿`）永远需要人。真正的语义判定要靠第 ④ 步的 LLM 复审层。
   此外 B 的规则全部从 **val.pdf 一本书**的 165 条人工裁定中蒸馏而来。`glued_digit_tokenisation` 是对质量门正则的结构性修正、可放心推广；其余参数（术语文档频率 2%、拉丁占比 40%/50%、文献条目判定）只在这一本上量化过。
3. **捕获层覆盖度无度量**。第 105 页 4 个 "true" 单元格未被捕获、以原文显示——这类漏捕获**根本不产生翻译单元**，因此无论验收单还是分诊都看不见它。逐页"提取文字量 vs 渲染文字量"对账是第 ③ 步的内容，也是目前最大的盲区。
4. **通用性未验证**。A、D 的单元测试用合成 PDF，真实数据验证只有 val.pdf 一本。第 ③ 步才会用 3–5 本不同风格的 PDF 标定边界。
5. `--auto` 的完整链路**未在真实 442 页上端到端跑过**：val 的页级产物早已齐备，重跑会覆盖唯一可回退成品，因此只做了非破坏性核对（442/442 页断点齐全、分块计划覆盖全书）。驱动逻辑本身由 `tests/test_render_driver.py` 用假子进程覆盖成功/崩溃重试/重试耗尽三条路径。

## 据实区分

- **文件已生成**：`acceptance-report.json` 可对任意已渲染产物生成。
- **可用版本已通过**：val.pdf 的两个成品经自动验收判定为 `deliverable_with_known_issues`。
- **无人值守能力已具备**：**部分**。渲染能自己跑完、交付判断能自动做出、人工复核清单已从 213 条降到约 23 条，且台账让重跑同一本书收敛到接近零。但**首次跑一本新书仍需人看那 23 条**，且捕获层漏捕获仍不可见（第 3 点）。"一次跑完即可交付、无人介入"尚未成立。
- **版本已发布**：否。
